# Design Decisions

The provided specification documents (Classroom_Survey_Web_App_Specification.md, DATABASE.md, API.md, UI.md) are kept unchanged. Where they conflict or leave a question open, the decisions below apply and **take precedence over the specifications**.

Priority order used: assignment instructions → this file → provided specifications.

---

## D1 — Student survey URL uses a public slug

**Specs said:** TODO.md used `/s/:surveyId`; UI.md, API.md and DATABASE.md use `/s/:slug`; DATABASE.md §6 allowed UUIDs for a first version.

**Decision:** The student route is `/s/:slug`, using `surveys.public_slug`.

- The slug is short, random, non-sequential and unique (for example `x7kf2q`).
- It is generated by `activate_survey` the first time a survey is activated, and kept afterwards.
- Raw survey UUIDs are never used in public URLs.

**Why:** Three of the four documents already use slugs, and a short slug is easy to read from a projector and type by hand.

---

## D2 — Students load surveys through one public function: `get_public_survey`

**Specs said:** UI.md and TODO.md require separate "Survey closed" and "Survey not found" screens, but DATABASE.md §8 only lets anonymous users read **active** surveys. Under those rules, a closed survey looks the same as one that doesn't exist.

**Decision:** Add a database function `get_public_survey(p_slug text)`, defined with `security definer` and callable by the `anon` role. It returns:

| Survey state | Returned value | Student screen |
|---|---|---|
| Active | `{ "status": "active", "survey": {...}, "questions": [...] }` with choices, ordered by `position` | Survey form |
| Closed or archived | `{ "status": "closed" }` | "This survey is no longer accepting responses." |
| Draft, or slug not found | `null` | "Survey not found." |

- No response or result data is ever returned.
- If a survey closes while a student has it open, the submission fails with `SURVEY_NOT_ACTIVE` and the "closed" screen is shown.

**Why:** This gives the exact screens UI.md describes while keeping students unable to see instructor-only data. Loosening the security rules instead would let anyone list all closed surveys.

---

## D3 — Every question is required

**Specs said:** API.md defines `MISSING_REQUIRED_ANSWER` and TODO.md says "Validate required answers", but TODO.md Phase 9 also says "Clearly label unanswered questions", and the schema has no `required` column.

**Decision:** Every question must be answered before a student can submit.

- **Frontend:** Submit shows inline errors next to unanswered questions and does not send the request.
- **Database:** `submit_survey_response` rejects a submission with `MISSING_REQUIRED_ANSWER` unless every question in the survey has exactly one answer. The check also runs here because the frontend can be bypassed.
- **Results:** every question's response count equals the survey's total responses, so percentages share one denominator.
- "Clearly label unanswered questions" is read as **"label questions with no responses yet"** (for example, before any student has submitted).

**Why:** It's the simplest rule, it uses the error code and TODO item that already exist, it needs no schema change, and it suits short in-class checks.

---

## D4 — Only Draft surveys can be edited

**Specs said:** TODO.md only blocked editing **active** surveys "unless first closed", which allowed editing closed surveys. The assignment says the instructor can "Edit existing **draft** surveys."

**Decision:** The editor opens only for surveys with status `draft`. Active, closed and archived surveys cannot be edited; use **Duplicate** to make an editable copy.

**Why:** The assignment requires it, and editing a survey that already has responses would delete or detach stored answers (questions cascade-delete answers; deleted choices set `answers.choice_id` to null).

---

## D5 — Students reach the database only through two functions

**Specs said:** DATABASE.md §9 says anonymous users "need INSERT access" to `responses` and `answers`, but also recommends a submission function. DATABASE.md §8 gives anonymous users direct read access to active surveys, questions and choices.

**Decision:**

- Student submissions go only through `submit_survey_response(p_survey_id, p_anonymous_token, p_answers)`, defined with `security definer` and callable by `anon`. It runs every check from DATABASE.md §9, plus D3 and D7, in one transaction.
- There are **no** INSERT policies for `anon` on `responses` or `answers`.
- The anonymous SELECT policies on `surveys`, `questions` and `choices` from DATABASE.md §8 are **not created**; `get_public_survey` (D2) replaces them.
- Row Level Security stays enabled on all five tables. Authenticated policies (DATABASE.md §10) are unchanged.

**Why:** The assignment requires that students cannot modify surveys or access instructor-only results. With this setup, the only things a student can do are load one active survey and submit one validated response. The duplicate check needs to read `responses`, which students can't, so the function must run with elevated access.

## D6 — Public sign-ups disabled; accounts created by hand

**Specs said:** DATABASE.md §10 gives full access to any authenticated user. If Supabase's public sign-up is left on, anyone could register and see every result.

**Decision:**

- Public sign-ups are disabled in Supabase Auth settings.
- The instructor account is created manually in the Supabase dashboard.
- A separate test account for grading is created the same way. Its login is submitted privately through HuskyCT and never committed to the repository.

**Why:** It closes the open-registration gap, and it covers the assignment's requirement to let the instructor test the interface without exposing credentials in the repository.

---

## D7 — An anonymous token is required for every submission

**Specs said:** `responses.anonymous_token` allows null, and the unique index ignores nulls, so a submission without a token bypasses duplicate protection.

**Decision:**

- The browser creates a token with `crypto.randomUUID()` on first visit and keeps it in localStorage.
- `submit_survey_response` rejects a missing or empty token. The frontend shows its generic error message.
- A repeat submission from the same token returns `DUPLICATE_RESPONSE`, which shows "You have already submitted a response to this survey."

**Why:** The assignment asks for "reasonable protection against accidental duplicate submissions." A per-browser token plus the database's unique rule meets that. It doesn't stop deliberate repeats from a private window, which the assignment doesn't require.

---

## D8 — Survey status changes only through specific actions

**Specs said:** API.md "Update Survey" allowed `status` and `public_slug` to be edited directly, which would skip the slug creation and auto-close done by `activate_survey`.

**Decision:**

- **Activate:** `activate_survey`
- **Close:** `close_survey`
- **Archive / Unarchive:** simple status updates, allowed only for the changes listed in D9.
- **Update Survey:** changes only `title` and `description`.
- `public_slug` is set only by `activate_survey`.

**Why:** It guarantees every active survey has a slug, so its QR code always works. The database's partial unique index separately guarantees that only one survey is active.

---

## D9 — Allowed status changes

**Specs said:** The four statuses were defined, but not which changes between them are allowed.

**Decision:**

| From | Allowed actions |
|---|---|
| Draft | Edit, Activate, Duplicate, Delete |
| Active | Present, Results, Close, Duplicate |
| Closed | Results, Reopen (Activate), Archive, Duplicate, Delete |
| Archived | Results, Unarchive (back to Closed), Duplicate, Delete |

- Reopening a closed survey keeps its slug and adds to the same responses.
- An active survey must be closed before it can be archived or deleted.
- Deleting a survey that has responses shows the stronger warning from UI.md §11.
- The dashboard shows only the actions allowed for each status.

**Why:** It covers every action required by the assignment and the spec, avoids surprises during class, and keeps data safe.

---

## D10 — A survey must be complete before it can be activated

**Specs said:** The spec says each survey has "one or more questions", but `activate_survey` didn't check anything.

**Decision:** A survey can be activated only if:

- it has at least 1 question;
- no question or choice text is blank;
- every multiple-choice question has at least 2 choices;
- every True/False question has exactly its two fixed choices (D13).

These are checked in the editor (shown next to the field, as UI.md §5 asks) and again inside `activate_survey`, which raises an error if any check fails.

**Why:** It prevents a broken or empty survey from reaching students during class.

---

## D11 — Confirm before activating while another survey is active

**Specs said:** Activation silently closes the survey that is currently active. UI.md requires confirmation for closing a survey, but not in this case.

**Decision:** If another survey is active, show: *"Activating "X" will close "Y". Continue?"* with Cancel and Activate buttons.

**Why:** It prevents accidentally ending a survey students are still answering, and matches UI.md's rule that destructive actions need confirmation.

---

## D12 — The Present page refreshes the response count automatically

**Specs said:** The assignment and UI.md require a response count on the Present page. Live updating (Supabase Realtime) is listed as post-MVP.

**Decision:**

- The Present page re-fetches the response count every **5 seconds** while it is open, and stops when the page is closed.
- The Results page keeps its manual **Refresh** button (UI.md §9).

**Why:** It meets the requirement without the extra Realtime setup. A single instructor page asking once every 5 seconds puts negligible load on the free tier.

---

## D13 — True/False questions use two fixed choices

**Specs said:** Submissions always send a `choice_id`, but nothing said how True/False options are stored or created.

**Decision:**

- When a question's type is True/False, the editor automatically creates two choices, "True" (position 1) and "False" (position 2), and shows them as read-only.
- Changing a question's type replaces its choices, after a confirmation if it already has choices.

**Why:** Storing True/False as ordinary choice rows means the results page, CSV export and submission function need no special cases, and the schema stays exactly as DATABASE.md describes.

---

## D14 — CSV export format

**Specs said:** API.md showed `question_1, question_2…` headers but also said the first row contains question text. TODO.md asked to export survey metadata. The spec said "export all survey results."

**Decision:**

- Export is **per survey**, from the Results page.
- One row per response.
- Columns: `survey_title`, `response_id`, `submitted_at`, then one column per question, ordered by position.
- Question column headers are the question text prefixed with its number, for example `Q1: What is required for recursion?`, so identical wording cannot collide.
- Each answer cell contains the chosen choice text.
- File name: `<survey-title>_<YYYY-MM-DD>.csv`.
- Values are escaped so commas, quotes and line breaks are safe.

**Why:** The `survey_title` column and the file name cover "export survey metadata" without extra rows above the header, which would break spreadsheet imports. "Export all survey results" is read as all results of the selected survey.

---

## D15 — Missing token error code: `MISSING_TOKEN`

**Specs said:** D7 requires `submit_survey_response` to reject a missing or empty token, but API.md's error list has no code for it.

**Decision:**

- `submit_survey_response` raises `MISSING_TOKEN` when `p_anonymous_token` is null or empty.
- The frontend shows its generic error message for this code. It should only happen if the browser blocks localStorage.

**Why:** Every rejection then has its own code, so the frontend can map each one to a message without parsing raw database errors (API.md §13).

---

## D16 — Dashboard date filter

**Specs said:** TODO.md Phase 10 asks for "filtering by date", but UI.md §4 only shows a search box and a status filter.

**Decision:**

- The dashboard adds **From** and **To** date inputs next to the search box and status filter.
- They filter by the survey's `created_at` date. Both are optional and include the dates chosen.
- All filters combine, and "No surveys match your search." (UI.md §10) shows when nothing matches.

**Why:** It covers the TODO item in the one place surveys are browsed, with no new page or schema change.

---

## D17 — Activate from the editor saves first

**Specs said:** The UI.md §5 editor has both **Save Draft** and **Activate** buttons, including on `/surveys/new`, but doesn't say what Activate does with unsaved changes.

**Decision:** Clicking **Activate** in the editor:

1. runs the D10 checks in the editor and stops with field errors if any fail;
2. saves the survey, creating it first when on `/surveys/new`;
3. asks for confirmation if another survey is active (D11);
4. calls `activate_survey`;
5. opens the Present page.

If a step fails, the editor stays open with the changes kept, and saved work is not lost.

**Why:** Students should never get an older version than what the instructor sees, and one click from editor to QR code suits preparing right before class.

---

## D18 — The database enforces the status and editing rules

**Specs said:** D4, D8 and D9 describe which edits and status changes are allowed, and D10 lists activation checks, but API.md only defines error codes for student submissions. Without database checks, a direct table update could skip these rules.

**Decision:** Triggers in the migration enforce the rules for every caller, and instructor actions use these error codes:

| Code | When |
|---|---|
| `SURVEY_NOT_FOUND` | `activate_survey` or `close_survey` is given an unknown survey ID. |
| `SURVEY_INCOMPLETE` | Activation fails a D10 check. The error's detail says which one. |
| `SURVEY_NOT_EDITABLE` | Changing the title, description, questions or choices of a survey that is not a draft (D4). |
| `INVALID_STATUS_CHANGE` | A status change not allowed by D9, making a survey active without `activate_survey`, changing `public_slug`, inserting a survey that isn't a new draft, or deleting an active survey. |

- Deleting a whole survey still removes its questions and choices (DATABASE.md §13).
- The rules are tested with `npm run test:db`, which runs the migration in PGlite (Postgres in WebAssembly) as both an anonymous student and a signed-in instructor.

**Why:** The rules hold even if the frontend has a bug or someone calls the API directly, so stored responses can't be detached from their questions by accident.
